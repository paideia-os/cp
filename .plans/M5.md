## Cross-repo dependencies at M5 close

- **paideia-as v0.33-crypto** — hard blocker for the two signatures.
  The release ships with placeholder signatures; the signing
  pipeline populates them once the crypto intrinsic lands. Consumers
  cannot `pkg install cp` until then (pkg refuses on verify-fail);
  the release ships in `pkgs.paideia-os/staging/` and promotes to
  `main/` after re-signing.
- **pkg.M4** — hard blocker for the mirror-push consumer path. The
  mirror-push manifest is in-tree; the fetcher-side install becomes
  runnable when pkg.M4 lands (pkg.M4 issue set is in
  `paideia-os/pkg` — see plan doc §5.1 for the issue titles).
- **doc.M1-002** — hard blocker for `doc cp` rendering. The
  `.pdxdoc` file is in-tree at M5-001; the render becomes visible
  when `doc` reaches a stable release. `--help` (via `pdx-help`) is
  a post-1.0 M6 concern per the CHANGELOG "Notes" section.
- **`pkgs.paideia-os` mirror infrastructure** — the manifest points
  at the canonical URL layout; the staging + main promotion path
  requires a running mirror. See `.plans/pkgs-mirror-push.md` for
  the specific URLs and their SLA.

## What M5 explicitly does not do

- **Does not compile a signed binary.** `paideia-as build` is a
  release-time invocation at the author machine, not a milestone-
  close deliverable in-tree. The `manifest.pdxsig` `payload:` lines
  use `<pending-build>` for artefact hashes; the signing pipeline
  populates them from the on-disk build output at release-tag time.
  Per the M5 no-build constraint (softarch never invokes build.sh
  under any circumstance), the in-tree manifest is the shape; main
  invokes the build at release time.
- **Does not promote to `pkgs.paideia-os/main/`.** The mirror-push
  manifest names the staging path; the promotion to main is a
  human-in-the-loop review step per §9.3 that runs off-repo.
- **Does not ship `help.pdx` / `tutorial.pdx` / `examples/`.** The
  I7 §2 (`doc <tool>`) deliverable lands at 1.0; I7 §1 (`--help`),
  §3 (`--tutorial`), §4 (`--examples`) land at post-1.0 M6 once
  `pdx-help` and `tutor` are stable. See CHANGELOG "Notes".

## Verification checklist (at release-tag time)

The signing pipeline runs `paideia-as release --lint` before
issuing either signature. Every check below is a one-line inspect
of an in-tree artefact:

1. `manifest.pdxproj` `version = 1.0.0` (not `0.4.0-m4`).
2. `manifest.pdxsig` `version = 1.0.0` matches `manifest.pdxproj`.
3. `manifest.pdxsig` `release_gates.m4_close_commit` is reachable
   in-tree (i.e. is an ancestor of HEAD).
4. `CHANGELOG.md` has a `## 1.0.0 — <date>` heading whose body
   enumerates every M1-M5 issue.
5. `doc/cp.pdxdoc` exists and lints clean under `pdx-help lint`
   (per §9.2 verify.sh).
6. Every `payload:` line names an existing repo-relative path.
7. Every `payload:` line's `<pending-build>` is replaced by a
   64-hex-char sha256 before the manifest hash is computed.

These seven checks are the M5 close preconditions for the signing
pipeline. Once all seven pass, the pipeline signs; the release is
then promotable to `pkgs.paideia-os/staging/` per `.plans/pkgs-
mirror-push.md`.
